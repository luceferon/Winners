# Решения: упрощение источников ставок

## Запрос

Убрать из создания и редактирования источника API-ключ, провайдера парсинга, тип и ручную надёжность. Надёжность должна определяться автоматически по результатам ставок источника.

## Подтверждённые решения

- Надёжность считается как доля выигрышей среди ставок со статусами `won` и `lost`.
- Статусы `pending`, `push` и `cancelled` не участвуют в расчёте.
- Если нет решённых ставок, API отдаёт `null`, интерфейс показывает «—».
- Провайдер выбирается только из общих настроек приложения; legacy-поля источника не влияют на парсинг.
- Если привязанное событие пришло от другого провайдера, движок ищет событие заново через общий провайдер, не передавая ему внешний ID от прежнего API.
- При ошибке внешнего провайдера движок не должен подменять результат симулятором `offline`.
- Старые колонки SQLite сохраняются, чтобы не требовать миграции и не удалять существующие данные.
- Тип и провайдер убираются также из таблицы источников; автоматическая надёжность показывается одной колонкой вместо ручного значения и дублирующей проходимости.

## Подход

Вычислять показатель по текущим данным при чтении источника. Это исключает рассинхронизацию при расчёте, изменении, переносе или удалении ставки и не требует фоновой синхронизации.

## Проверки

- API-контракт проверяется тестами на создание/редактирование, отсутствие решённых ставок и вычисление метрики.
- Выбор общего провайдера проверяется тестом движка парсинга.
- Перепривязка и отказ от симуляторного fallback проверяются тестами движка.
- Формы и таблица источников проверяются в браузере на временной SQLite-базе.
