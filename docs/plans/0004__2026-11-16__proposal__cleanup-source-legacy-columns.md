## Мотивация

После удаления модуля парсинга колонки `kind`, `provider_key`, `api_key`,
`reliability` в таблице `sources` не используются:
- `kind` (bookmaker/tipster/api/other) — не отображается и не влияет на логику.
- `provider_key` — использовался для выбора провайдера парсинга.
- `api_key` — хранил ключ провайдера.
- `reliability` — ручная надёжность, заменена на вычисляемую.

Они создают путаницу при чтении модели и не нужны новым разработчикам.

## Рассмотренные подходы

### Выбранный: миграция через пересоздание таблицы

Так как в проекте нет Alembic, а `create_all` не удаляет существующие
колонки, нужно:
1. Создать новую таблицу `sources_new` без legacy-колонок.
2. Скопировать данные (`id`, `name`, `url`, `enabled`, `notes`, `created_at`,
   `updated_at`) из старой таблицы.
3. Удалить старую таблицу и переименовать новую.

Это безопасный паттерн для SQLite, не требующий внешних инструментов миграции.

- Плюсы: чистая схема, данные сохраняются.
- Минусы: нужна миграция при старте (проверка наличия колонок).

### Отклонённый: оставить как есть

Оставить колонки в БД, но игнорировать. Отклонён: технический долг,
модель `Source` содержит поля, вводящие в заблуждение.

### Отклонённый: подключить Alembic

Полноценная система миграций. Отклонён как избыточный для одноразовой
очистки; лучше как отдельная задача, если схема будет меняться часто.

## Implementation Tasks

1. **Удалить legacy-поля из модели** — убрать `kind`, `provider_key`,
   `api_key`, `reliability` из `Source` в `app/models.py`. Убрать их из
   `Source.as_dict()` (если ещё там) и из схем.
   - Files: `app/models.py`, `app/schemas.py`, `app/seed.py` (DEMO_SOURCES).
   - Verification: `import app.main` работает, тесты проходят.

2. **Миграция при старте** — в `init_db()` (или `lifespan`) проверить, есть ли
   колонка `kind` в таблице `sources`; если есть — выполнить пересоздание
   таблицы с сохранением данных.
   - Files: `app/database.py` (или `app/migrations.py`).
   - Verification: тест на старой схеме с legacy-данными → после миграции
     данные сохранены, колонок нет.

3. **Очистка демо-данных** — в `DEMO_SOURCES` убрать `kind`, `provider_key`,
   `reliability`.
   - Files: `app/seed.py`.
   - Verification: `seed_demo_data` работает без legacy-полей.

4. **Тесты** — убедиться, что тесты источников не ссылаются на
   `kind`/`provider_key`/`api_key`/`reliability` как на редактируемые поля
   (надёжность — вычисляемая).
   - Files: `tests/test_api.py`.
   - Verification: `pytest` зелёный.

## Verification Strategy

- Тест миграции: создать БД со старой схемой (с legacy-колонками и данными),
  запустить `init_db`, проверить, что колонки удалены, а данные сохранены.
- Полный прогон `pytest` после изменений.
- Ручная проверка: интерфейс источников работает, надёжность вычисляется.

## Критические риски

| Риск | Важность | Снижение риска |
|---|---|---|
| Потеря данных при пересоздании таблицы | Высокая | Транзакция, копирование до удаления, бэкап `winners.db` перед запуском |
| Миграция не сработает на старой базе | Высокая | Проверка `PRAGMA table_info(sources)` перед миграцией |
| Сторонний код ссылается на legacy-поля | Средняя | grep по проекту перед удалением |
