### Brainstorming Summary

- Надёжность автоматически отражает проходимость ставок источника: выигранные / (выигранные + проигранные).
- Активные, возвращённые и отменённые ставки не входят в расчёт; при отсутствии решённых ставок интерфейс показывает «—».
- Новый источник использует общий провайдер парсинга из настроек приложения. Старые `provider_key` и API-ключи остаются в БД, но больше не влияют на парсинг и не показываются пользователю.
- Если уже привязанное событие принадлежит другому провайдеру, движок повторно найдёт его через общий провайдер; при отсутствии совпадения или сетевом сбое ставка не будет рассчитываться через симулятор.
- Поля типа, провайдера, API-ключа и ручной надёжности удаляются из форм. Колонки типа и провайдера удаляются из списка источников.
- Общий workflow и шаблон плана, на которые ссылаются установленные dev-skills, в пакете отсутствуют; план составлен по структуре из инструкции brainstorming.
- API regression tests: RED confirmed for manual reliability, empty values, and legacy provider selection.

## Кодовая база

- Источники ставок уже агрегируют `won`, `lost`, а также рассчитывают `win_rate_percent`.
- Отдельное `Source.reliability` редактируется в форме и может расходиться с фактической проходимостью.
- Парсер читает `Source.provider_key` для выбора провайдера, поэтому для новых и существующих источников это поведение нужно переключить на общую настройку.
- Форма и таблица источников находятся в `web/js/views/settings.js`; API и схемы — в `app/api/sources.py` и `app/schemas.py`.

## Рассмотренные подходы

### Выбранный: вычислять по ставкам при чтении

Использовать уже имеющиеся результаты ставок как источник истины и отдавать вычисленную проходимость вместо сохранённого ручного значения. Не требует миграции и остаётся актуальным при расчёте, редактировании, переносе и удалении ставки.

Сложность: низкая.

### Отклонённый: сохранять метрику в БД

Обновлять надёжность при каждом изменении результата. Отклонён: потребуется поддерживать синхронность также при удалении и переназначении ставок, а сохранённое значение может устареть.

### Отклонённый: удалить колонки источника миграцией

Физически убрать `kind`, `provider_key`, `api_key` и `reliability` из SQLite. Отклонён: миграция не нужна для пользовательского поведения и добавляет риск потери legacy-данных.

## Implementation Tasks

1. **Закрепить API-контракт тестами** — проверить, что ручная надёжность больше не меняет значение источника, а завершённые результаты формируют вычисляемый процент.
   - Files: `tests/test_api.py`, при необходимости `tests/test_engine.py`
   - Verification: узкий запуск новых тестов в красной фазе, затем зелёной
   - Risk: legacy-поля в БД; сохранить их, но игнорировать при записи и выборе провайдера.
2. **Вычислять надёжность на сервере и использовать общий провайдер** — строить метрику из текущих статусов ставок; перепривязывать события другого провайдера через общий, не передавать несовместимый ID и не подменять сетевой сбой симуляцией.
   - Files: `app/api/sources.py`, `app/schemas.py`, `app/parsers/engine.py`
   - Verification: тесты API и парсера
   - Risk: повторный поиск может не найти событие; оставить ставку на ручную проверку вместо неверного расчёта.
3. **Упростить интерфейс источников** — удалить ненужные поля из окон добавления/редактирования и колонки типа/провайдера из таблицы; показывать рассчитанную надёжность вместо ручной.
   - Files: `web/js/views/settings.js`
   - Verification: браузерная проверка таблицы, обеих форм и автоматического показателя.
   - Risk: старые значения на экране не должны просочиться через остаточные поля формы.

## Verification Strategy

Сначала добавить регрессионные тесты API для вычисляемой проходимости, отсутствия расчётных ставок и игнорирования переданных вручную `reliability`/`provider_key`. Затем выполнить полный `python -m pytest -q`. В браузере проверить, что в создании и редактировании отсутствуют API-ключ, провайдер, тип и ручная надёжность, а список показывает «—» либо актуальный процент.

## Критические риски

| Риск | Важность | Снижение риска |
|---|---|---|
| Внешний ID события несовместим с общим провайдером | Высокая | Перепривязать матч через общий провайдер; при сбое не использовать симуляцию и не менять статус ставки. |
| Ручное legacy-значение будет выглядеть как достоверная метрика без решённых ставок | Средняя | Расчёт отдаёт `null`, UI отображает «—». |
| Изменение API нарушит старые значения источников | Низкая | Не удалять DB-колонки; убрать только пользовательское управление и влияние на парсинг. |

## Out of Scope

- Удаление legacy-колонок из SQLite и миграция существующих баз.
- Изменение общей настройки провайдера парсинга или её ключей.
- Изменение правил расчёта выигрыша/проигрыша по счёту матча.
